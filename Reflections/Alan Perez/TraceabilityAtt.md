# Traceability Attribute

The usability attribute selected for this reflection is low error rate. It was chosen as one of the three usability attributes for the project because <mark>in a clinical scheduling system, a mistake like a duplicate appointment, a missing patient, or a conflict between a therapist and a room can have a real operational impact.</mark> That justification made it one of the most important attributes to trace from concept to prototype.

In terms of how it was included in the prototype, low error rate was not left as just an idea, it became a set of concrete rules built into the critical flows of the Agenda Module. When creating an appointment, the system validates working days, office hours, and checks that neither the therapist nor the room has a scheduling conflict. For rescheduling, the system verifies that the appointment exists and is in a valid state before allowing any changes. In mass rescheduling, affected appointments are identified, resources are released, and they are sent to a follow-up queue. There are also alternative flows where the system warns the user about a conflict and asks for confirmation before saving. <mark>This shows that the attribute was implemented mainly as error prevention and conflict handling within the prototype flows.</mark>

To measure this attribute, the team formalized three metrics following the ISO/IEC/IEEE 15939:2017 standard. The main one was **M-01 — Rate of Avoidable Errors Committed by the User**, defined as the proportion of incorrect actions that could have been prevented by system mechanisms, with the formula *Avoidable errors committed / Total actions executed × 100* and an acceptance threshold of ≤ 5%. This was complemented by **M-02**, which measured recovery time after an error, and **M-03**, which recorded whether the user completed the task without restarting or abandoning the flow.

The data collected was very specific to each metric. For **M-01**, every action that produced an unintended result when the system already had a prevention mechanism available, such as a disabled option, a prior warning, or a confirmation dialog, was recorded. For **M-02**, the seconds between the moment the user detected the error and the moment they corrected it were measured. For **M-03**, a binary value was registered indicating whether the task was completed without restarting or abandoning the flow. <mark>Sessions were also recorded in audio and analyzed from transcripts, which allowed the team to estimate the values of each metric across participants.</mark>

<mark>The reason those specific data points were chosen is that they answer the core question of the attribute directly: not just whether the user finishes the task, but whether the system actually prevents errors, allows fast recovery, and avoids the user getting lost or starting over.</mark> That connects well with the project context, since the target users are administrative staff between 40 and 62 years old with different levels of digital literacy, where even a small mistake in the interface can have a real impact on the clinic's daily operations.

As alternative data that could have been collected to measure the same attribute, the number of extra clicks or steps needed to correct an error, the amount of evaluator interventions, the severity of each error, the percentage of tasks completed without assistance, or even a classification of errors by type such as navigation errors, data entry errors, or misinterpretation of messages could all have been used. <mark>These would have measured the same idea from a different angle, but the data the team selected is more direct and easier to connect to error prevention and recovery within the clinical workflow.</mark>
